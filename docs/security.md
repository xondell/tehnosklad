# Модель безопасности и RLS

## Роли

- `admin` — полный доступ к каталогу, заявкам, журналам, настройкам и ролям.
- `editor` — управление каталогом и медиа без управления пользователями, ролями и секретными журналами.
- `anon` — чтение только опубликованного каталога и публичных настроек.
- `authenticated` без прикладной роли не получает административных данных.

Роль хранится в защищённых `users`, `roles`, `user_roles`, а не в изменяемом пользователем `user_metadata`. Email и пароль остаются только в `auth.users`.

## Политики

- RLS включён на каждой таблице `public`.
- Публичные policies проверяют не только дочернюю строку, но и опубликованного, неархивного родителя.
- Черновики, архивы, пользователи, заявки и технические журналы закрыты по умолчанию.
- `private.has_app_role()` размещена в неэкспонируемой схеме, имеет фиксированный пустой `search_path`, полностью квалифицированные имена и минимальный `EXECUTE` grant.
- Administrative UPDATE всегда защищён и `USING`, и `WITH CHECK` через `FOR ALL` policy.
- Защита маршрута `/admin` нужна для UX, но окончательная авторизация выполняется RLS и серверной проверкой роли.

## Заявки

Браузеру не выдаётся право вставки в `leads`. Публичный серверный endpoint должен добавить:

- ограничение тела запроса;
- схему валидации и нормализацию телефона;
- обязательное согласие и версию текста согласия;
- honeypot;
- rate limit по хэшу IP/сессии;
- уникальный `client_request_id`;
- нейтральные ответы без внутренних ошибок.

## Секреты

`SUPABASE_SERVICE_ROLE_KEY`, Telegram token/chat ID и AI key — только server env. Они не хранятся в `site_settings`, логах или `NEXT_PUBLIC_*`.

## Storage

На Этапе 3 bucket `product-images` должен получить:

- публичное чтение только опубликованных изображений товаров;
- запись/замену/удаление только admin/editor;
- whitelist MIME и максимальный размер на bucket и сервере;
- сгенерированный сервером безопасный путь;
- отдельные INSERT, SELECT и UPDATE policies для upsert.

## Дополнительные меры следующих этапов

- Валидация всех входящих данных на сервере.
- CSP после определения реальных внешних источников; базовые безопасные заголовки уже включены.
- CSRF-защита для cookie-auth мутаций через проверку Origin и механизмы Next.js Server Actions.
- Минимизация PII в assistant/Telegram logs и политика срока хранения.
- Проверка Supabase Security/Performance Advisors перед применением миграций.
